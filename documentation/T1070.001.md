# T1070.001 — Indicator Removal: Clear Windows Event Logs

## Attacker behavior

After gaining access, attackers clear event logs to remove evidence of their
activity (anti-forensics). Common methods:
- `wevtutil cl Security` / `wevtutil cl System` / `wevtutil cl Application`
- Event Viewer GUI → "Clear Log"
- API calls (ClearEventLog) via scripts or tools

## Detection logic

Windows documents log clearing itself:
- Clearing the **Security** log generates **Event ID 1102** inside the Security log
  (the record is written AFTER the clear, so the attacker cannot remove it)
- Clearing other logs generates **Event ID 104**

Legitimate clears are rare in production endpoints → high-fidelity signal.
Severity split: Security clear = critical (12), other logs = high (8),
because Application/System clears can be caused by maintenance or installers.

## Rule

`rules/defense-evasion/T1070.001_eventlog_cleared.xml`
- rule 100101 → Event ID 1102 (Security cleared), level 12
- rule 100102 → Event ID 104 (other logs cleared), level 8
- MITRE ATT&CK mapping: T1070.001

## Lessons learned

- Built-in Wazuh rules 63103/63104 detect log clearing but at low severity (level 3/5)
- Custom child rules 100101/100102 elevate severity to 12/8 and add explicit MITRE ATT&CK mapping
- Child rule approach preserves built-in detection while improving alert prioritization
- MITRE ATT&CK module correctly shows T1070.001 under Defense Evasion tactic
- Validation confirmed: anti-forensics activity detected in real-time with proper severity
